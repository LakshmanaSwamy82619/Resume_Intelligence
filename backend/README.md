# AI-Powered Resume Intelligence & Candidate Matching — Backend

A production-style FastAPI backend for hybrid-retrieval, multi-agent resume/candidate matching,
built to the "AI-Powered Resume Intelligence & Candidate Matching" specification.

> **Status**: core pipeline (auth, ingestion, hybrid retrieval, reranking, four agents, ranking,
> evaluation, notifications, admin/HR APIs) is implemented and passes an end-to-end automated
> test suite (33 tests) against SQLite. Postgres+pgvector, Redis, and Celery are wired and
> documented but were not exercised against a live Postgres/Redis instance in this environment
> (see "Known limitations").

```

  db/              async engine/session, portable Vector column (pgvector | JSON)

  providers/
    llm/           LLMProvider, KeyGatewayLLMProvider, deterministic fallback, fallback chain
    embeddings/    EmbeddingProvider, local (sentence-transformers), hashing fallback, chain
    reranker/      RerankerProvider, cross-encoder, heuristic fallback, chain
  retrieval/       lexical (TF-IDF), semantic (pgvector | brute-force numpy), hybrid, filters
  ranking/         configurable weighted final-ranking framework
  agents/          4 agents + sequential orchestrator + shared state
  evaluation/      ranking, labeled skill-gap and evidence-grounding metrics; dataset and runner
  services/        auth, resume ingestion, job, search orchestration, notifications, email
  workers/         Celery app + bulk-processing/email background tasks
  api/v1/          all REST routes
alembic/           DB migrations (autogenerated initial schema + pgvector index migration)
tests/             unit / integration / performance
docker-compose.yml backend + postgres(pgvector) + redis + worker
```

## 2. Environment variables

See `.env.example` for the full, commented list. Key ones:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | `sqlite+aiosqlite:///...` for zero-dependency dev, or `postgresql+asyncpg://...` for production |
| `LLM_PROVIDER` / `LLM_BASE_URL` / `LLM_MODEL` | `openai` for OpenAI chat completions, or `keygateway` for the ArshnivLabs OpenAI-compatible endpoint |
| `EMBEDDING_PROVIDER` | `local` (sentence-transformers, falls back to offline hashing) or `keygateway` (unverified, see below) |
| `RERANKER_PROVIDER` | `local` (cross-encoder, falls back to lexical heuristic) |
| `JWT_SECRET_KEY` | **Generate your own.** Never reuse a secret that has appeared in chat/tickets/screenshots. |
| `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` | Creates the first Admin user on startup if no admin exists yet |

### KeyGateway capability notes (Section 11 — what we verified vs. assumed)

We were given `LLM_BASE_URL=https://keygateway1.arshnivlabs.com/v1` and `LLM_MODEL=gpt-4o-mini`,
and found no public documentation for this gateway. What this implies and what we built:

- **Chat completions**: the `/v1` + model-name shape strongly implies an OpenAI-compatible
  `/v1/chat/completions` route. `KeyGatewayLLMProvider` calls exactly that, nothing else.
- **Embeddings**: **not confirmed to exist.** `KeyGatewayEmbeddingProvider` implements the
  standard OpenAI-compatible `/v1/embeddings` call shape *in case* the gateway supports it, but
  `EMBEDDING_PROVIDER=local` is the shipped default. Do not flip this to `keygateway` in
  production until you've confirmed the route responds (a bad/missing endpoint just makes every
  embedding call fall back to the offline hashing provider, silently degrading retrieval quality
  from semantic to lexical-only).
- **Reranking**: no evidence of a rerank endpoint on this gateway, so no
  `KeyGatewayRerankerProvider` was built — only the local cross-encoder + heuristic fallback,
  per the spec's explicit "don't pretend a capability exists" instruction (Section 11).

## 3. How to run

### Option A — Docker Compose (full stack: Postgres+pgvector, Redis, worker)
```bash
cp .env.example .env   # then edit JWT_SECRET_KEY, LLM_API_KEY, BOOTSTRAP_ADMIN_* etc.
docker compose up --build
```
The `backend` service runs `alembic upgrade head` before starting Uvicorn. API docs at
`http://localhost:8000/docs`.

Before starting the stack, set a non-empty `JWT_SECRET_KEY` and a URL-safe `POSTGRES_PASSWORD`
in `.env`. Production mode requires a JWT secret of at least 32 characters. The Compose password
has no insecure built-in default; Compose refuses to start without it.

### Option B — Local, zero-dependency dev (SQLite, no Redis/Celery)
```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Leave DATABASE_URL as the default sqlite+aiosqlite:// line
# Set CELERY_TASK_ALWAYS_EAGER=true so bulk uploads run inline without a Redis broker
uvicorn app.main:app --reload
```
Tables are auto-created on startup when `DATABASE_URL` starts with `sqlite` (see `app/main.py`).
For Postgres, use Alembic instead (`alembic upgrade head`).

### First login
Set `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` in `.env` before first startup — this
creates the one and only bootstrap Admin. From there, Admin creates HR accounts via
`POST /api/v1/admin/hr-accounts`.

## 5. Design decisions & trade-offs

- **Vector storage is dialect-portable** (`app/db/base.py::PortableVector`): a real `pgvector`
  column on Postgres, a JSON-encoded float list on SQLite. This lets the whole project run with
  zero external services for evaluation, while production gets real ANN search. The SQLite path
  is a brute-force O(N) numpy scan — correct, not scalable. **This is the main documented gap
  against the "10,000+ resumes" target in this environment** (no live Postgres was available to
  benchmark against here).
- **No hard-coded 70/30 ranking formula** (Section 18): `app/ranking/config.py` defines seven
  named, independently-computed factors with justified default weights, structured so an
  evaluation run against a labelled dataset can re-tune them later.
- **Every external AI dependency degrades, never fails**: LLM → deterministic template,
  neural embeddings → offline hashing vectorizer, cross-encoder reranker → lexical heuristic.
  Every search response reports `ai_provider` / `fallback_used` / `fallback_reason` /
  `processing_mode` truthfully.
- **Structuring/extraction is rule-based, not LLM-based**, so it never depends on an external
  call to produce evidence-grounded candidate facts (Section 13). JD requirement *labelling*
  (mandatory vs. preferred) can optionally be LLM-refined but never LLM-invented — the model is
  only allowed to re-classify terms the rule-based pass already found, never add new ones.
  See `app/ingestion/jd_extraction.py` docstring.
- **Agent orchestration is plain async function composition, not LangGraph** (Section 45): the
  four agents form a strictly sequential pipeline with no branching for this use case, so a full
  graph-execution framework would add indirection without changing behavior. `AgentState` is a
  plain dataclass specifically so swapping in a LangGraph `StateGraph` later is a localized change.
- **Mandatory-skill filtering is soft, not hard** (Section 15): a candidate missing a mandatory
  requirement is down-ranked, not silently excluded from the pool, so recruiters can still see
  near-miss candidates and why.

## 6. Evaluation (Section 22/23)

No ground-truth Top-3 dataset was provided, and none was invented. Instead:

1. `POST /api/v1/evaluation/datasets` — create a named dataset
2. `POST /api/v1/evaluation/datasets/{id}/queries` — add representative queries
3. `POST /api/v1/evaluation/queries/{id}/labels` — a human labels candidate relevance (0/1/2)
4. `POST /api/v1/evaluation/run` — runs the **actual** search pipeline against every labelled
   query and computes Precision@K / Recall@K / MRR / NDCG from the results vs. the human labels

Per-search evidence-grounding and fallback-usage stats are also available without any labelled
data, via `GET /api/v1/hr/searches/{id}/evaluation`.

## 8. Known limitations (honest, not hidden)

- **Not benchmarked at 10,000+ resumes.** This sandbox had no Postgres+pgvector instance to load
  data into. The architecture (pgvector ivfflat index, hybrid retrieval → pool of ~100 →
  rerank → top ~20 → deep agent analysis) is designed for that scale, but the number itself is
  unverified here. `tests/performance/test_scale.py` is a ready-to-run harness for validating this
  against a real Postgres instance.
- **Rule-based structuring will miss unconventional phrasing.** A skill mentioned only in an
  unusual sentence structure with no taxonomy match won't be captured. The taxonomy
  (`app/ingestion/skills_taxonomy.py`) is a living list, easy to extend, not exhaustive by design.
- **OCR requires system binaries** (`tesseract`, `poppler`) not guaranteed present outside the
  Docker image; the ingestion pipeline degrades gracefully (keeps the page's text empty and logs
  it) rather than crashing if they're missing.
- **KeyGateway embeddings/reranking are unverified** (see Section 2 above) — shipped disabled by
  default.
- **`sentence-transformers` (and `torch`) were not exercised in this development environment**
  (no access to download model weights here), so the neural embedding/reranking path is
  implemented and unit-tested for its *fallback* behavior, but the neural path itself should be
  smoke-tested once deployed somewhere with model-download access (e.g. via `docker compose up`,
  which has full internet egress).
- **Rate limiting is in-memory**, documented in `app/utils/rate_limit.py` as needing a Redis
  backend for any multi-process/multi-pod deployment.
- **Semantic near-duplicate detection is not implemented** — only exact file/content-hash and
  identity-fingerprint duplicate detection (Section 27's baseline requirement), by deliberate
  choice to avoid false-positive-merging two different candidates (documented in
  `app/ingestion/dedup.py`).

## 9. Data visibility and ownership

The application currently models one shared candidate knowledge base, not isolated HR tenants. HR users and Admins can browse and search the shared candidate/resume pool; resume uploads record the uploader for audit but do not make the candidate private. Candidate detail and resume download follow that shared-pool policy.

Jobs, searches, bulk-processing jobs, and evaluation datasets are HR-owned. An HR user can read or use only records they created. Admins have platform-wide access to administrative accounts, audit logs, analytics, and evaluation execution; HR-owned candidate and search data is not exposed through Admin-only list APIs unless an endpoint explicitly documents it.

## 10. Remaining work for frontend integration

- OpenAPI schema is auto-generated at `/openapi.json` (`/docs` for Swagger UI) — the React
  frontend can codegen a client directly from it.
- File upload endpoints (`/api/v1/resumes/upload`, `/bulk-upload`) expect `multipart/form-data`.
- All list endpoints currently return arrays directly (not `{items, total}` envelopes) except
  `/api/v1/candidates` which is paginated — consider standardizing before frontend integration
  if pagination is needed elsewhere (e.g. search history at scale).
- CORS is controlled via `CORS_ORIGINS` env var — add the deployed frontend origin there.
